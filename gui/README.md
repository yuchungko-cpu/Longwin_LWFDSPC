# LWFDSPC 主機端工具 (X2CScope / UART2) — V1.0

給 Longwin LWFDSPC 滑板車控制器用的 PC 端診斷與調校介面，走韌體裡既有的
X2CScope 連線，**不需要改韌體**。

版本號與韌體版本各走各的：本工具是 **V1.0**（`x2c_vars.py` 的 `GUI_VERSION`，
git tag `gui-v1.0`），韌體版本由 GUI 從目標端讀回來顯示，不寫死在主機端。
`python motor_gui.py --version` 或 `python check_link.py --version` 可以問出來。

X2CScope 走專屬的 **UART2 (RB8 = U2TX / RB9 = U2RX)**，與 RS485/Modbus 儀表用的
UART1 分開，所以接上主機不會干擾儀表通訊。

### Baud rate

韌體端改**一行**就能換速度（`diagnostics_x2cscope.c`）—— divider 與 BRGH 模式都由算式
自動推導，不需要手算，也不會出現「改了 divider 卻忘了改註解」的分歧：

```c
#define X2C_BAUD_TARGET  X2C_BAUD_230400     // ← 只改這裡
```

| 選項 | divider | 模式 | 實際 baud | 誤差 |
|---|---|---|---|---|
| `X2C_BAUD_57600` | 107 | 標準 | 57,870 | +0.47% |
| `X2C_BAUD_115200` | 53 | 標準 | 115,741 | +0.47% |
| `X2C_BAUD_230400` | 26 | 標準 | 231,481 | +0.47% |
| `X2C_BAUD_460800` | 53 | **高速** | 462,963 | +0.47% |

四個選項誤差都是 +0.47%，與原本 115200 相同 —— 時鐘容差上沒有新風險。460800 會自動
切到高速模式（BRGH=1）：標準模式在那個速度 divider 只剩 12，誤差會跳到 +4.34%。
算式優先選標準模式（每 bit 取樣 16 次、抗雜訊較好），只在誤差 >1% 時才用高速。

誤差超過 2% 會**編譯失敗**（負長度陣列斷言，XC16 是 C99 沒有 `_Static_assert`），
不會燒進板子才發現。

主機端 `x2c_vars.py` 的 `DEFAULT_BAUD` 必須一致，否則**完全連不上**（握手就失敗，
不是資料錯）。埠掃描在主 baud 全數失敗後會自動退回 `LEGACY_BAUD`（115200）再掃一輪，
所以燒舊韌體的板子仍然連得上；標題列會顯示 `COM15 @ 115,200 (舊 baud)` 並轉成橙色。

## 定位

**觀測 + 調校參數寫入**，不是「從 PC 開車」。

參考專案 mclv48v300w 的韌體有一整組 `apiData.*` 讓主機下命令；**本專案沒有**。
這顆控制器的命令來源是油門/VR、煞車開關、排檔開關與 Modbus 儀表。韌體裡唯一叫
「Scope」的三顆變數（`g_i16ScopeCmdTarget` / `RateLim` / `Out`）是純觀測用的取樣點，
不是命令入口。

## 安裝

**Python 3.10 ～ 3.14（64-bit）**，建議 **3.13 或 3.14**。

這個範圍不是我們挑的 —— `pyx2cscope` 與 `mchplnet` 的 metadata 寫死
`Requires-Python: >=3.10,<3.15`，裝 3.9 或 3.15 時 pip 會直接拒絕安裝。
本工具自己的程式碼只用到 3.7 等級的語法與 API，所以下限完全來自相依套件。

從 [python.org](https://www.python.org/downloads/windows/) 下載 Windows 安裝檔，
安裝時**確認勾選 `tcl/tk and IDLE`**（預設已勾）。沒有 tkinter 的散布版
（embeddable zip、部分 conda 環境）開不起 GUI。

### 還需要一份 ELF —— 它不在 git 裡

本工具靠 ELF 的 DWARF 除錯資訊取得每個全域變數的位址，所以**沒有 ELF 就不能連線**。
而 `.gitignore` 排除了 `dist/`，所以剛 clone 下來的工作目錄裡**沒有** ELF：

```
LWFDSPC.X/dist/default/production/LWFDSPC.X.production.elf
```

先在 MPLAB X 建置專案產生它。而且必須是**你真正燒進那塊板子的那一份** ——
理由見下面的〈位址哨兵〉：換了一次建置，位址就全部位移。

`x2c_vars.py` 會自動挑專案裡 mtime 最新的 `.elf`；要指定別份就用 `--elf <path>`。

### 最省事的方式：雙擊 `gui\run_gui.bat`

它會自動挑一個版本合格的 Python（優先 3.14 → 3.13 → …）、檢查 tkinter、
缺套件就問你要不要裝，然後開 GUI。也可以帶參數：

```
run_gui.bat                 自動掃 COM port 並連線
run_gui.bat --demo          無硬體，只驗版面
run_gui.bat --port COM12    指定序列埠
run_gui.bat --read-only     完全停用寫入
```

失敗時視窗**不會**自動關閉（會 `pause`），所以雙擊執行也讀得到錯誤訊息。

### 手動方式

```powershell
python --version                          # 應落在 3.10 ~ 3.14
pip install -r gui/requirements.txt
python gui/check_link.py --scan           # 先確認通訊
python gui/motor_gui.py
```

| 版本 | 狀況 |
|---|---|
| 3.14 | **完整驗證過**（3.14.7 / Tcl-Tk 9.0） |
| 3.13 | 相容範圍內，建議值 |
| 3.12 | Tk 8.6 相容性已實測（clam 主題、`sashpos`、`option_add` 皆正常） |
| 3.10 / 3.11 | 可用，但會裝到較舊的 matplotlib / numpy |
| 3.9 及更早、3.15 及更新 | **pip 會拒絕**（pyx2cscope 的硬限制） |

## 三支工具，照這個順序用

### 1. `check_link.py` — 連線自我測試（無 GUI）

**先跑這支。** 它把通訊問題（COM port 錯、板子沒供電、ELF 不對版）與 GUI 問題
隔開來，免得在圖形介面裡瞎猜。

```powershell
python gui/check_link.py                 # 自動掃描 port，再跑完整檢查
python gui/check_link.py --list          # 只列出序列埠 (★ = 會被掃描)
python gui/check_link.py --scan          # 只掃描，找出 X2CScope 在哪個埠
python gui/check_link.py --port COM12    # 指定埠
```

它會依序驗：ELF 能不能解析 → 必要變數在不在 → build 有沒有比原始碼舊 →
連線 → **位址哨兵** → 每顆變數讀一次 → 換算成物理量 → 狀態機解碼 →
EMB 夾煞路徑計數 → 主迴圈與 X2CScope 鏈路健康度。

### 2. `motor_gui.py` — 儀表板

```powershell
python gui/motor_gui.py --demo           # 無硬體，驗版面與換算
python gui/motor_gui.py --port COM12
python gui/motor_gui.py --port AUTO --read-only
```

左側三張即時捲動圖（命令鏈 km/h、速度誤差、電流 A），上方有 **暫停繪圖 / 清除**：

- **暫停**只凍結繪圖，**遙測輪詢與右側分頁照常更新** —— 暫停的用途是把剛剛那一段
  抓在畫面上看清楚，不是中斷與車子的連線。暫停時每張圖右上角會標「⏸ 已暫停」，
  因為凍住的曲線與「鏈路掛了」長得一模一樣。
- **清除**清掉所有軌跡，要看下一次動作的乾淨波形時比等舊資料滾出去快。
- **滑鼠移過去**會出現垂直十字線與讀值方塊（`-7.8 s` + 各軌跡的值）。對齊到最近的
  **取樣點**而不是游標像素 —— 顯示內插值會讓人以為那是量到的東西。靠右邊時方塊自動
  翻到游標左側；最新那點顯示「現在」而不是「-0.0 s」。
- **計數器歸零**記下當前的單調計數器值當基準，之後每一列多顯示自基準以來的增量。
  見下方「計數器與增量」。

右側十三個分頁：

| 分頁 | 內容 |
|---|---|
| 執行狀態 | `uGF` 旗標、馬達停止/方向、e-lock |
| 命令鏈 | ①油門目標 → ②限斜率 → ③送往速度環 → ④refSet，加量測速度與速度環輸出 |
| 電源溫度 | 電池、DC bus 電流、Iq、控制器/馬達溫度、溫控區間、各種有效旗標 |
| 輸入 | 油門 mV 與有效行程 %、IEMB、助力段位、儀表控制模式 |
| 電磁煞車 | 狀態、夾煞原因、EMB PWM 釋放度、**五個夾煞路徑計數器** |
| 感測換相 | Hall 週期/邊緣數/狀態位元、換相角 |
| 故障警報 | 警報位元圖展開、`FaultFlags` |
| 鏈路健康 | 主迴圈頻率、X2C RX/TX FIFO 丟棄、Modbus 計數 |
| 組態 | 韌體版本、極對數、輪徑、速度來源等**執行期實際值** |
| 調校 | `WRITE_TUNING` 24 項可寫參數 |
| ⚠ 危險 | `WRITE_DANGER` 11 項，預設鎖住 |
| 刻度 | 主機端換算參數，即時重算 |
| 寫入紀錄 | 每次寫入的時間、寫入值、回讀值、結果 |

`--demo` 用合成訊號跑一輪「起步 → 巡航 → 放油門 → 停車 → 夾煞」，不開序列埠。
用途是無車驗證版面與換算，**不是**假裝有量到東西 —— 標題列會標明「模擬模式」。

### 3. Scope 擷取視窗（從儀表板按「開啟 Scope 視窗」）

與捲動圖根本不同：目標端在 ADC ISR 裡（20 kHz）把通道寫進自己的 5000 byte
緩衝區，擷取完成後才整批傳回。所以這裡是 **50 µs 解析度的真波形**，而輪詢遙測
只有幾十毫秒 —— 斜率限制器的暫態、換相抖動只有在這裡看得到。

- 45 條精選通道，外加從 ELF 自由挑選（595 個純量，帶搜尋）；自加的通道會存進
  `scope_custom_channels.json` 跨 session 保留
- 一次最多 8 條（X2CScope 傳輸協定的硬限制）
- 按下擷取前就顯示**預估點數與視窗長度**，免得抓不到想看的暫態
- 觸發：來源、位準（附 Q15 → km/h 提示）、邊緣、延遲 %、Auto/Triggered
- 縮放/平移/存圖、CSV 匯出（含時間軸與取樣條件註解）

Scope 視窗**不自己開連線** —— 一個 COM 埠只能開一次，所以它與儀表板共用同一條
`x2c_link.Link`。

### 軌跡樣式：遞減線寬，不是虛線

疊圖時最後畫的那條會吃掉每一個像素，量測疊在命令上就會把命令整條藏起來 ——
而那正是最想看的情況。解法用**遞減線寬**（1.9 → 0.8 px）而不是虛線：重疊時較粗的
底層會從較細的上層兩側露出來，效果一樣，但在密集/雜訊大的軌跡上不會糊掉。

虛線碰上 625 點的高頻振盪時，虛線間隔會與訊號互相干擾，整條變成一片霧，
單根尖峰也會被切碎看不出來。真的需要虛線區分時可以勾「虛線區分重疊軌跡」（預設關閉）。

### 游標讀值放在表格，不畫在圖上

滑鼠移過波形時會出現垂直十字線，各通道的值顯示在下方統計表的**「游標值」欄**，
時間顯示在 Y 軸下拉旁（`游標 t = 880.000 ms (#352)`）。

讀值刻意**不畫在圖上**。原本用 matplotlib 的 text artist 顯示，實測
`draw_artist(text)` 要 **10.7 ms/次**（5 行文字 + 圓角框 + alpha 合成，每次重做排版），
加上整個 axes 的 blit 共 **70 ms/次** —— 滑鼠每秒上百個事件時等於 700% CPU，
事件佇列塞爆、Tk 的 `drain()` 被排擠、畫面反而停止更新，看起來就像斷線。

改成表格欄位（`Treeview.set()` 是微秒級）後：

| 版本 | 每次成本 |
|---|---|
| 讀值畫在圖上 + blit 整個 axes | 70.0 ms |
| blit 整個 axes | 17.8 ms |
| 讀值移到表格 | 3.38 ms |
| **只 blit 十字線移動過的窄長條** | **0.52 ms** |

TkAgg 的 blit 要把 ARGB 緩衝逐像素複製進 Tk PhotoImage：整個 axes（817×495 = 404k
像素）要 3.0 ms，160px 寬的長條只要 0.85 ms。長條必須涵蓋**舊位置與新位置的聯集**，
只複製新位置的話舊那條線不會被蓋掉，會留下殘影。

放在表格也不只是更快：位置固定、不遮住波形、與旁邊的 min/max/平均並排更好對照。

### 擷取期間遙測會暫停

這是刻意的。擷取時目標端同時在跑 20 kHz 的 ADC ISR 寫自己的緩衝區、主迴圈，以及
回應主機的 LNet 來回；讀回 5000 byte 要 20 次連續的 253-byte 傳輸。若同時還在輪詢
遙測，兩件事會互相搶傳輸，而底層對此**完全沒有防護**：

- `mchplnet` 的 `LNetSerial.read()` 不驗 SYN、盲目相信長度位元組。一個被截斷的回應
  會留下殘留位元組，讓**後續每一個**框架連鎖錯位。
- `pyx2cscope` 的 `_read_array_chunks()` 把每個區塊的讀取失敗**吞掉**（只寫 log），
  然後回傳短少的緩衝區。少掉的位元組讓通道解交錯整體錯位 ——
  畫出來是一張看起來很像真波形、實際上毫無意義的圖。

所以本工具：擷取全程停止遙測輪詢、每次擷取邊界清空序列埠收接緩衝區重新對齊、
失敗自動重試兩次，並且**檢查點數完整性**（低於預期 98% 就當失敗，不畫）。
若仍失敗，訊息會附上目標端的 `RX/TX FIFO 丟棄` 與 `Update 跳過` 計數 ——
那是「主迴圈是不是曾長停頓」的直接證據。

擷取完成後標題會寫出實際點數；與預期不符時標題轉紅並標「資料不完整」。

### Scope 的問題永遠不會弄掉連線

`_service_scope()` 與 `_arm_scope()` 都會走到真的碰序列埠的呼叫（`request_scope_data`、
`is_scope_data_ready`），那些會拋例外。所有這類呼叫都包在 `_safe_service_scope()` 裡，
失敗時只結束**這一次擷取**並顯示「連線維持」——
遙測與 Scope 是兩件獨立的事，不該互相拖累。

另外，任何一次變數讀取失敗都會**清空序列埠收接緩衝區**。這是必要的：讀取拋例外代表
那個框架已被放棄，而它剩下的位元組還躺在緩衝區裡；`LNetSerial.read()` 不驗 SYN、
盲目相信長度位元組，所以那些殘留位元組會讓後續**每一個**框架連鎖錯位 ——
一次逾時就變成永久失步，接著每次讀取都失敗直到觸發斷線門檻。
清掉緩衝區把「永久失步」降級成「掉一個取樣」。

「ELF 全域」的符號表也改成**切到那個分頁時才載入**（1.5 秒的 DWARF 解析），
開 Scope 視窗本身因此是純 UI 動作。

## COM port 自動掃描

埠預設是 **AUTO**，不需要自己知道是哪一個。按「連線」（或「掃描」）時會：

1. 列舉序列埠，**跳過藍牙虛擬埠** —— 它幾乎不可能是除錯 UART，而「開啟」一個沒有
   連線的藍牙埠可能阻塞數秒（`serial.Serial()` 的 timeout 只管讀寫，管不到 open 本身）。
   要一併試的話加 `--include-bluetooth`。
2. 把描述像 USB 轉序列的埠（`USB Serial`、`CP210x`、`CH340`、`FTDI` …）排前面，
   讓掃描早點命中 —— 每個沒回應的埠要付一次約 1–2 秒的握手逾時。
3. 逐一做**真正的 LNet 握手**（`get_device_info`）。握手成功是目標端有沒有在跑
   X2CScope 的決定性證據；只看埠的描述字串猜不出來，同一條 USB 線插到任何板子上
   描述都一樣。
4. 找到就停，把埠填回下拉選單並接著連線。

掃描過程逐埠回報在狀態列，所以不會出現「畫面靜靜卡十幾秒」。找不到時會分開列出
**已探測**與**已跳過**的埠 —— 混在一起講會讓人以為藍牙埠已經排除掉了。

> pyx2cscope 本身也支援 `port="AUTO"`，同樣是做真握手。這裡自己掃是為了拿到進度
> 回報、跳過藍牙埠，以及失敗時講得出到底試過哪些埠。

## 兩件會讓你被誤導的事

### 位址哨兵

`diagnostics_x2cscope.c` 裡的 `g_u16X2cDiagSignature` 是固定常數 `0xA5C3`。

**每次重新建置後全域變數位址都會位移**（linker 用 `--no-gc-sections`，位址依連結
順序變動）。如果主機拿舊的 ELF 去讀新韌體，讀到的會是錯位的**別的變數** —— 數字
看起來很合理但完全沒有意義。韌體註解裡就記著曾被這件事誤導過。

所以連上線的第一件事就是驗這一格。哨兵不符時：

- 標題列的哨兵標籤轉紅
- 紅色橫幅明示「畫面上每一個數字都是錯位的別的變數，全部作廢」
- **所有寫入被封鎖**（往錯誤位址寫入在實車上不只是顯示錯）

另外，只要有任何韌體原始檔比 ELF 新，就會警告 build 過期 —— 那種情況下每個變數
都還解析得出來，所以在寫入落到錯誤位址之前什麼異狀都看不出來。

### 讀回目前值

「調校」與「危險」兩頁各有一顆**「讀取目前值」**鈕，把 40 個可寫參數從韌體讀回來
（約 80 ms）。這一組**刻意不做週期輪詢** —— 它們絕大多數只在開機初始化時被寫，
一直重讀只是白花頻寬，而頻寬該花在捲動圖的時間解析度上。

另外，**每次寫入之後那一列會自動用回讀值更新**。這對 `loop` 類的參數特別重要：
你會當場看到韌體把它蓋回去，不必去翻寫入紀錄比對。

讀取不需要解除危險組的鎖定 —— 看現在的值本身沒有風險，看不到現值就動手才有風險。

## 計數器與增量

`鏈路健康` 與 `電磁煞車` 兩頁的計數器**全部是 `uint16_t`，上限 65,535，會迴繞**
（已逐一對 ELF 驗證）。而且是**開機後累計**，最大用量還是歷史高水位、永遠不會下降。

所以光看數字無法回答實驗最想問的那件事：**「我剛改的設定，讓它停止增加了嗎？」**
`RX FIFO 丟棄 = 27` 可能是開機那兩秒就發生完的，也可能正在持續增加 —— 兩者意義完全
相反，但畫面上長得一樣。

因此有獨立的**「增量」欄**：

| 欄位 | 數值 | 增量 |
|---|---|---|
| X2C RX FIFO 丟棄 | `27  << 丟位元組 -> 框架失步` | `自連線 +0` |
| X2C RX FIFO 最大用量 | `127 / 127 (100%)  << 已填滿` | `自連線 +0` |
| X2C Update 被跳過 | `60,528 / 65,535  (會迴繞)` | `自連線 +22,528` |

- **自連線**：連線後第一輪掃描完成（約 1 秒）自動記下基準，不用按任何按鈕。
  這是為了把**韌體啟動期的一次性事件**與本次 session 分開 —— 實測 `RX FIFO 丟棄`
  固定是 27、`最大用量` 固定填滿 127、`TX 最大用量` 固定 416，跨電源重置都一樣，
  那是連線握手時灌進來的，不是持續發生的故障。
- **自歸零**：按「計數器歸零」手動重新取基準，優先於自連線基準。用來做 A/B 對照。
- `+0` 也會顯示 —— 「確認沒有增加」與「不知道有沒有增加」是兩件事。

增量一律用**模數算術**（`(new − old) % 65536`）。直接相減在迴繞後會得到負值，
而負值看起來像「韌體重置了」—— 實測被這件事誤導過：`58,538 → 6,588` 直接相減是
`-51,950`，其實是 `+13,586` 的迴繞（`g_u16X2cUpdateSkipCount` 在 ADC ISR 裡以最高
20 kHz 遞增，約 3.3 秒繞一圈）。

> 也因此**無法**用這些計數器偵測韌體重啟：迴繞與歸零在 16 位元容器裡長得一樣。
> 要判斷重啟得靠韌體記錄 `RCON`，那是目前拿不到的東西。

`X2C Update 被跳過` 的絕對值幾乎沒有意義（會迴繞），只有增量有意義。它也**不是**頻寬
指標，而是 `DiagnosticsStepIsr()` 的重入保護：ADC ISR 在主迴圈正跑
`X2CScope_Communicate()` 時觸發就跳過 `X2CScope_Update()` —— 那段時間 Scope 取樣有缺口。

### FIFO 用量會標出飽和

環形緩衝區的可用量是 `SIZE-1`，所以看到 `127 / 127` 或 `511 / 511` 就是**填滿**，
已經在丟位元組。75% 標「接近上限」、到節流點標「已達節流點」、填滿標「已填滿」。

TX 的 `416` 不是巧合：`X2C_TX_FIFO_READY_MARGIN = 96`，`Communicate()` 在剩餘空間
少於 96 時就跳出迴圈，也就是用量到 `512 − 96 = 416` 就觸發節流。看到 416 代表 TX
正持續頂在節流點上 —— 那是提高 baud 的直接理由。

## 框架失步：為什麼哨兵每個週期都要驗

**失步不會拋例外。** `LNetSerial.read()` 盲目相信長度位元組、不驗 SYN，串流錯位時它
照樣讀出一個框架形狀的位元組塊並回傳 —— 只是讀到的是**別的變數**。所以靠 try/except
完全抓不到，畫面上會出現 Iq 變成速度、DC bus 變成 1300 A 這種**看起來像真資料的垃圾**。

`g_u16X2cDiagSignature` 是固定常數 `0xA5C3`，所以它是現成的框架對齊校驗碼。本工具在
每個輪詢週期的**讀值前後各驗一次**，兩次都對才把這一輪的資料發出去 —— 相當於給整個
週期加一個 checksum。任一次不對就**整輪丟棄**，不畫、不更新分頁。成本 4 ms/週期。

> 停止更新是刻意的。顯示錯位的值比不顯示更糟 —— 前者會讓人拿錯誤的數字判斷車輛行為。

偵測到失步後的復原階梯（由弱到強）：

1. **清收接緩衝區**（清兩次，中間留 50 ms）。只清一次會漏掉「還在路上」的位元組。
2. **關掉再重開序列埠**。清緩衝區只能丟掉**已經到達**的位元組；擷取失敗時目標端可能
   還在傳一個沒被讀完的 253-byte 陣列回應，那些位元組清了又來。重開埠是唯一能把
   驅動層緩衝與在途資料一起丟乾淨的方法。
3. 兩者都無效才跳紅色橫幅，並說明這**不是** ELF 版本問題（連線時哨兵是對的）。

重新對齊後橫幅自動消失、寫入權限恢復。權限是從**連線時的授權**重算，不是
`writes_allowed and ok` —— 後者一旦被壓成 False 就再也回不來，一次偶發失步之後就永遠
不能寫入了。

Scope 套同一個閘門：擷取前確認對齊，讀回 20 個區塊後再確認一次。位元組數對得上
並不代表內容對得上 —— 失步時每個區塊都「讀得到」，只是讀到偏移過的位址。
擷取失敗時**先修好框架再讀健康計數**，否則計數器本身也讀不到（先前就是這樣顯示
「讀不到（目標端沒有回應）」），而且會把一條失步的鏈路直接交還給輪詢迴圈。

## 「讀不到」與「讀到錯的值」是兩件事

哨兵有三種狀態，**必須分開處理**：

| 狀態 | 意思 | 處置 |
|---|---|---|
| `ok` | 讀到 `0xA5C3` | 正常，資料發出去 |
| `desync` | 讀到值，但不是 `0xA5C3` | 框架真的錯位 → 走復原階梯（清緩衝區 → 重開埠） |
| `noreply` | 讀取逾時 / 拋例外 | 目標端沒回話 → **不要**重開埠 |

把後兩者混為一談會出事：對 `noreply` 套重開埠只會把一次暫時失誤放大成自我維持的故障
—— 每個週期重開一次，而每次重開又讓接下來幾筆交易失敗，於是永遠出不來
（症狀是狀態列卡在「序列埠已重開，正在確認框架對齊 …」）。
重開埠因此另有 **8 秒最短間隔**，且重開後會等 250 ms 讓鏈路穩定才判斷。

### 目標端卡死：主機端救不了

連續約 3 秒完全讀不到任何值時，工具會**停止重試**並明確要求**重置控制器電源**。

這不是放棄治療 —— 清收接緩衝區與重開序列埠都只動到 PC 這一側，碰不到目標端
X2CScope 的狀態機。無限重試只是裝作還在努力。

已知觸發條件：**Scope 讀回在中途失敗**。pyx2cscope 的 `_read_array_chunks` 會吞掉失敗的
傳輸區塊並繼續往下走，目標端可能因此卡在「還要再送 N 個位元組」的狀態。
降低發生機率：取樣分頻調大、通道數減少、或先停用 Modbus 儀表以降低主迴圈負擔。

> 韌體側已排除的：`UxSTA.OERR`（接收溢位會讓 dsPIC 的接收硬體停擺）**已經**在
> `diagnostics_x2cscope.c` 的 `_U2RXInterrupt` 裡清掉了，所以卡點不在那裡。

## 寫入的 persist 語意

`WRITE_TUNING` / `WRITE_DANGER` 每一項都標了 persist：

- **開機值**（`boot`）—— 只在開機 / 馬達重新初始化時被寫。改了會一直有效，
  直到下一次 stop→start 回到編譯值。
- **主迴圈會覆寫**（`loop`，橙色徽章）—— 主迴圈或某個任務每個 tick 都重寫這一格。
  從主機寫進去只會存活幾毫秒。

`loop` 的項目仍然列出來，因為「寫了沒反應」本身就是需要被看見的事實。
所以**每次寫入都會立刻回讀**，把「寫入值 → 實際值」記進寫入紀錄 —— 回讀值與
寫入值不同不是錯誤，那是唯一能證明韌體把它蓋回去的證據。

典型例子：`piInputOmega.piState.outMax`（速度環電流上限）被溫控任務每個 tick
重寫，所以從主機改它一定無效；要改電流上限得改溫控門檻或 `TorqMode_IqMax`。

## 配色

淺色主題（白底）。軌跡顏色是為白底挑的，對白色都有 ≥3:1 的對比、文字 ≥4.5:1。

要換回深色主題的話，這三處要**一起**改，只改其中一處會讓圖變成一片空白：
