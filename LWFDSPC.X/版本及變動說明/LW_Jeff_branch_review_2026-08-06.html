一句總結：實質上是一次調參 + 一個 EMB 狀態機補洞 + 兩個 Modbus bit 修正。全部只有 3 處真正改變行為的程式碼，其餘是 #define 數值、enum 改名與註解。沒有新演算法。
命令單位換算（看懂所有數字的前提）：1 count = 0.366 馬達 RPM = 0.00069 km/h；1 霍爾邊緣 = 車輪 1.75 mm；1 pulse/100ms = 33.3 馬達 RPM = 0.063 km/h。

A1 修的是什麼問題

訊號用哪個命令鬆油門後多久失效
狀態切換 bIsActiveg_stSystemData.i16TargetRpm（main.c:1401）
= 未平滑的原始油門目標		1 ms 內歸零 → 狀態立刻離開 RELEASED
倒溜計數器武裝piInputOmega.inReference（main.c:2827）
= 平滑後的實際命令		走 step/time 減速斜坡（−25~−40 counts/ms），約 140~460 ms 後才降到武裝門檻以下

補洞前 bRollbackDetected 只在 RELEASED 被檢查，於是那 0.14~0.46 s 的空窗裡「訊號還活著，但沒有任何狀態在看它」。此時車正在倒溜，速度高於 UVW 進鎖門檻 → Plan A / Plan B 同時失效 → 只剩 3 s failsafe（且從命令歸零才起算），倒溜距離遠超「不得超過 1/4 車輪 = 159 mm」的規格。

A1 的分支優先順序（插入後）

WAITING_TO_LOCK:
  1. bIsActive            → 回 RELEASED（重新給油門）
  2. bRollbackDetected    → 立即 LOCK + 閂鎖        <-- 新增
  3. bReverseEdgeDetected → 立即 LOCK（Plan B，需 UVW lock 已生效）
  4. bUVWLockActive       → 延遲 50 ms → LOCK（Plan A 主路徑，正常停車走這條）
  5. else                 → 命令歸零後 3000 ms failsafe
次要觀察：該分支設的 s_bRollbackLatched 在此狀態幾乎空轉 —— 能走到分支 2 就代表分支 1 未成立，亦即 bIsActive == false 必為真，下一拍進 LOCKED 時 if (!bIsActive) 立刻解閂。不是 bug，但註解說的「立即鎖定 + 閂鎖」只有前半段有實際作用。

bcc1671 的 commit message 寫的實際
「change the reverse-edge counter to decrement instead of hard-reset on a direction-matching edge」 沒有。bcc1671 完全沒有動到 main.c（該 commit 只含 5 個檔案：embraker.c/h、logic_motor.h、temp_controller.h、userparms.h）。main.c:2837 仍是 g_u8EmbRevEdgeCnt = 0; // 方向一致 → 清零；origin/main..origin/LW_Jeff 在這段的 diff 為 0 行
這一項缺席與 B 表的 REV_EDGES = 90 相乘 = 洞補了但通道被堵住。門檻 90 加上硬歸零，代表坡上車體晃動使方向偶爾翻一次，累積的 89 個邊緣就全部清光 → 計數永遠到不了 90。這兩個改動本來是配套的，只進了一半。結論：A1 補好的分支，實務上比改動前更難觸發。
