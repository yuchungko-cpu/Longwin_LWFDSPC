1Bugs fixed

#ProblemCause and fix
1Assist level 0 still crept forward at 1.04 km/h; reverse was not blocked at all The level cap table's entry 0 is 0, but three OUTPUT_MIN floors downstream promoted it back to 1500 counts. Present in V0.16 too, masked by the EMB release threshold of 1600 (1500 < 1600, so the brake never released — the motor was instead stalling against a clamped brake). Lowering that threshold to 800 made the creep visible.
Fixed by returning target 0 at level 0 before any floor applies, direction-agnostic so forward and reverse are blocked together, plus an EMB gate that prevents any command source from releasing the brake at level 0. Deliberately not an immediate hard lock, so dropping to level 0 while moving decelerates smoothly first. Now called e-lock.
2Powered-rollback detection could never trigger uphill The counter required consecutive reverse hall edges and reset to 0 on any same-direction edge. During a PI-versus-gravity tug of war the counter was zeroed every cycle while net displacement kept growing past the 1/4-wheel spec. Changed to net counting (reverse +1, forward −1, floor 0).
3Rollback counter froze at standstill, causing a re-lock deadlock The counter is only updated inside the hall-edge ISR, so with the vehicle clamped and still, nothing ran — not even the disarm path. It stayed at or above threshold, so re-applying the throttle re-locked on the next 20 ms tick before the wheel moved, and clearing the count requires motion. Now cleared on EMB LOCK and RELEASE.
4Assist level index read past the array Modbus delivers 4 bits (0–15) but the cap table has 6 entries and the index was never bounds-checked. Now clamped; levels 6–15 behave as level 5.
5Standstill speed zeroing had never worked MotorStartSpeedPulses was initialised to 0 and never assigned, so the guard was always false. X2CScope showed the effect: after a stop, a final hall edge decoded as reverse (brake-clamp rebound) held the measured speed at −900 counts for 840 ms until the timer-1 timeout. The command was already 0, so the speed loop saw a positive error and drove the motor forward — harmless only because UVW short and EMB usually clamped first. Set to 3 (0.19 km/h); the residue now clears within one 100 ms latch period.
6A04 / A19 alarm codes swapped EMB sensor fault was on A19 and motor hall fault on A04, the reverse of spec. Swapped, and the EMB fault bit added to the Modbus LCD error register.

2New: deceleration command filter

The higher speed-loop gains faithfully amplified the command steps on throttle release and on level changes, which the rider felt as a jolt. The acceleration side already had rate-limit plus a first-order filter; the deceleration side went through the old step/time table. It now has its own filter, with four independent quadrants: forward/reverse × accel/decel.

ItemDetail
7 selectable decel curves R from 20 to 100 counts/tick, i.e. 1200 ms down to 240 ms for full travel. Curves 4 and 6 match the old table's −25 and −40. Its selector is independent of the accel curve, since deceleration is safety-relevant and should not follow the rider's chosen accel level. Currently set to curve 2 (800 ms).
Rate limiter needed a down branch It previously snapped straight to target whenever the target dropped, so a decel rate parameter would have had no effect whatsoever. This was the single most important implementation detail.
Min-RPM floor gated to accel only On the decel path it would pin the command at 1500 counts, so the vehicle could never stop and UVW/EMB could never engage — the stop chain needs the command to be exactly 0.
Snap-to-zero threshold The filter tail is asymptotic: about 240 ms at K=4 before the output rounds to 0, and at K ≥ 10 integer decay sticks at 1 count forever.
Reverse got its own parameters Found that reverse had been silently using the forward accel curve — the filter call had no direction gate. Reverse 0→2.76 km/h was taking about 0.63 s against the 5–8 s its own step/time table intended, roughly 8× faster, with a preload jumping straight to 38% of reverse full speed. Defaults deliberately reproduce that existing behaviour, so reverse feel is unchanged this release and is now tunable.
The step/time tables and their ramp function are untouched and remain the fallback when the filter is disabled. Note they are still computed every cycle but no longer used on the live path, so tuning them now has no effect.

2EMB failsafe has no speed gate
✓ closed 08-13 — intentional, not a defect		 As observed this week: on a downhill the UVW path cannot engage (wheel speed too high), Plan B depends on UVW, and rollback detection is disarmed once the command decays — so only the 3000 ms failsafe remains, and it clamps regardless of speed. Shortening it to 1000 ms was discussed but not applied at the time.

Follow-up 08-13: the absence of a speed gate is deliberate design. If the command has been zero for the whole timeout and the vehicle is still moving, every normal deceleration and holding path has already failed — at that point continued motion is itself the hazard, so the vehicle must be stopped regardless of speed. The jolt and pad wear are an accepted cost. A speed gate must not be added for ride comfort, as it would disable the last line of defence exactly when it is needed.
Comfort is instead addressed by letting an earlier path catch the case: the new downhill-slide detector (EMB_DOWNHILL_*, v0.20) clamps after 42 mm of travel, while kinetic energy is still negligible. EMBRAKER_LOCK_TIMEOUT_MS was separately shortened 3000 → 1000 ms on 08-10. See s_logic_embraker.h for the recorded intent
3600-count steady-state gap at full speed Command 12000 but measured speed plateaus at 11400 (7.87 versus 8.29 km/h). A PI with integral action should drive steady-state error to zero, so this is output saturation. Source not yet confirmed — bus voltage (25 V is known to give only about 7.1 km/h) or the temperature current clamp. Scope piOutputOmega.out against outMax to tell them apart
